# Three binary save slots and restoring a playthrough

[Guide home](../README.md) · [Controls](../01-controls.md) · [Script index](../ScriptReference/README.md)

**Workbook areas:** `Save File`.

## What gets saved

Three independent `slot-1.sav` through `slot-3.sav` files live beneath `Application.persistentDataPath/Saves`. They contain party stats/progress, equipment, inventory copies, gold, selected character, world seed/settings, position, opened chests, defeated encounters, audio/display settings, playtime, and visited dungeon layouts/progress.

## Saving, step by step

1. `GameSave.Capture` converts live scene state into plain `SaveData`.
2. Items/equipment are recorded by names resolved through the item catalog.
3. `BinarySaveFile.Write` validates the data and writes primitives/arrays in a fixed order.
4. A header stores `WISE`, schema version 3, payload length, and SHA-256 checksum.
5. The complete temporary file replaces the prior file. Save & Quit returns to the title only after a successful write.

## Loading, step by step

Read verifies size, version, checksum, and value bounds before scene restoration. GameSave runs early and installs the saved world seed before generation. Later it restores party/inventory and dungeon progress, then reveals the scene.

Version 2 binary saves are readable. A legacy version 1 JSON file has a one-time import path. A checksum detects corruption; it is not encryption or proof a file has not been deliberately edited.

## Why binary is used

Fixed primitive values avoid JSON field-name/text-number overhead and make the schema explicit. The tradeoff is that reader and writer must agree on field order and version. This uses BinaryReader/BinaryWriter, not BinaryFormatter.

## Restore behavior to remember

- Continue is based on **last played**, not only last saved.
- A dungeon save resumes in its first room with its layout/progress, not the exact saved room position.
- An ordinary battle save restores the encounter return position; it does not resume halfway through an attack animation.
- Save is rejected during travel.
- Deletion requires the title UI confirmation and affects one slot.

Seeds reproduce generated terrain under the current algorithm. Changing that algorithm can require save migration even if the stored seed stays the same.

## Demonstrate it yourself

Use a spare slot. Gain gold or an item, switch character, save through Quit, then Continue and compare. In a dungeon, open a progression chest, save, and confirm the first-room resume plus preserved key/chest state. Do not use your only valuable slot for deletion testing.

## Explain it in one answer

“Capture makes a data snapshot, the binary writer stores an explicit versioned schema with a corruption checksum, and loading restores the seed before generating the world.”
